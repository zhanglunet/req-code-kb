# req-code-kb MVP 方案（2026-11-24，待用户过目）

## 一句话

不把整仓代码倒进知识库，而是按“需求”建库：一个需求进来，只备齐这一个需求要用的最小完备上下文，沉淀成一页“需求知识页”；需求越多，库越完善。

打个比方：做一道菜只备齐这道菜要用的料，不把整个菜市场搬进厨房。

## 1. 三路来源怎么进库

所有来源最后都落成统一的一条记录：`{来源类型，来源定位，文本片段，关联需求 id}`。来源定位精确到行（代码 `文件:行号`、需求文档段落、群消息 id+时间），每条知识都能溯源。

### 路 1：代码仓库

- 输入：GitHub 仓库地址（MVP 先支持本地 clone / 已下载的目录，clone 用 shallow）。
- 解析：Python 标准库 `ast` 抽符号（函数/类定义、import、调用关系），**零依赖，不引 tree-sitter**（留接口，以后换）。
- 排序：借鉴 Aider repo map 的思路自己重写——调用关系构图 + PageRank 排序。PageRank 打个比方：像论文引用一样，越多人引用的函数越重要。
  - Aider 的 `aider/repomap.py` 已核实存在（27,306 字节，Apache-2.0），思路可借鉴；MVP 代码自写（约 200 行），不直接拷，避免长期依赖一个 2026-05-22 后提交放缓的项目。
- 范围：MVP 只扫 `.py` 文件。

### 路 2：需求文档

- 格式：按 github/spec-kit 的 spec 模板写 Markdown（标题 / 背景 / 验收标准三段）。非模板文档也接受，降级为全文检索。
- 种子提取：文档里反引号中的标识符（函数名、类名、文件名）+ TF-IDF Top-K 关键词。TF-IDF 打个比方：在人群里喊名字，喊“张伟”没用，喊全名加工号才定位到人——词越稀有、越能定位，权重越高。
- 一份需求文档 = 一个需求 id（`REQ-xxx`），是全库的主键。

### 路 3：飞书群消息

- MVP 只做“导出文件进库”：群消息先导出成 JSON / Markdown（lark-cli 导出或手动导出），每条带时间、发送人、群名；只索引与需求关键词相关的片段，**不整群倒灌**。
- 现场演示用已脱敏的导出样本，不现场连飞书（避开权限/租户问题）。
- 纪律不变：飞书只读不写，不自动发消息。

## 2. “最小完备上下文”的边界（可执行的定义）

- **种子**：需求文档里的标识符 + TF-IDF 命中的符号。
- **扩展**：调用图上走 1 步的邻居（直接调用 / 被调用）必进；走 2 步的邻居只进 PageRank 分数高于阈值的。k-hop 打个比方：沿着调用关系走一两步的邻居，再远就不认了。分级见 §11④：full 走满 2 跳，lite 只走 1 跳，vibe 只给种子文件。
- **截断**：默认 token 预算 8,000（约 20 个文件片段），超了按 PageRank 从低往高砍。
- **排除**：测试文件、文档、CHANGES 只有在需求明确提到测试/文档时才进；`examples/` 按需进。
- **人确认**：先出“候选上下文清单”给人勾选（Sweep 的“需求→检索→计划”链路），确认后才入库沉淀。MVP 用命令行交互确认（y/n），演示时展示这一步。
- **重叠归并**：两个需求共享同一文件/函数时只存一份，挂两个需求 id（多对多映射表 `kb/index.json`）；知识页里标“也被需求 X 引用”。
- **“死需求、死代码不用管”的判定**：MVP 不自动判定生死——只记“最后被引用时间 + 引用次数”，超过 90 天零引用标“疑似沉寂”，删不删由人定。谁来判定什么是死的，得有依据，不能凭感觉漏掉以后还要用的东西。

## 3. 需求知识页（固定结构，沉淀物）

每页存 `kb/requirements/REQ-xxx.md`：

1. 需求原文（摘录 + 来源链接）
2. 相关文件 / 函数清单（带 `文件:行号` 链接）
3. 调用链 Mermaid 图（1–2 跳）
4. 影响面：种子符号的上游调用者（改动先波及谁，每文件前 3 个）
5. 群消息佐证（有才写，没有写“暂无”）
6. 验收对照：真实改动文件清单（验收用）
7. 回流记录：需求做完后，真实改动与预测的对照（`reqkb harvest` 追加，不改沉淀）

## 4. 问答（MVP 分两档，诚实分档）

- **必做**：零依赖 TF-IDF 检索（FDE 机器人同款做法）→ 取 Top-5 片段 → 拼成提示词 → 打印出来，每条带引用来源。
- **演示时**：把拼好的上下文现场贴给大模型问一句（人肉走 LLM 这一步），不把 LLM 调用写进 MVP——现场网络/模型不可控，写进去是翻车点。
- 不内置任何模型 key、不调任何付费接口。

## 5. 验收标准（盲测，不是自说自话）

主验收：拿一个**同类新需求**跑一遍，看召回的相关文件是否覆盖真实改动文件。

- **盲测用例（已核实）**：pallets/click PR #3896《给 `CliRunner.invoke` 加 `context_settings` 参数》，2026-11-06 已合并。输入只给需求描述（PR 标题 + 正文，隐去改动文件），输出必须包含核心改动文件 `src/click/testing.py`；5 个真实改动文件（`src/click/testing.py`、`tests/test_testing.py`、`tests/test_termui.py`、`docs/testing.md`、`CHANGES.md`）中至少命中 3 个。
- **副验收**：同仓 PR #3878（不同需求，同模块）同样跑一遍，核心文件也是 `src/click/testing.py`，验证不是偶然命中。局限先说明：两个用例都在同一模块，跨模块用例后续再补。
- **规模目标**：输出文件数 ≤10 个，且 ≤ 全仓 py 文件数的 15%（click 全仓 91 个 py 文件 → ≤10 个，约 11%）。
- **工程验收**：零依赖（只用标准库）、单命令跑通（`python -m reqkb build --req ...`）、Mermaid 图能渲染、PR 只开不合。

## 10. 盲测方法与实测结果（2026-11-24，MVP 实现后补记）

盲测不是拿已合入的代码跑一遍，而是回到改动之前：

- #3896 的测试仓库是 click 在合并提交 `fdb65f4` 的第一父提交
  `dd149eb3` 时的状态（改动尚未存在）；#3878 用的是其合并提交
  `ac0e297` 的第一父提交 `2247b35e`。输入只有需求文档（改动文件
  已隐去），输出再对照真实改动文件。
- `CHANGES.md` 的条目是 PR 本身加进去的，改动前不存在，所以它
  原则上不可召回：#3896 最高可命中 4/5，#3878 最高可命中 3/4。
  验收线（#3896 ≥3/5、#3878 ≥2/4）就是按这个上限定的。

实测（`python3 tests/test_blind.py`，2026-11-24，全部通过）：

2026-11-24 晚补记：中文分词修复后重测，召回不变（#3896 3/5、

根本不是候选。修法是排序保底：需求点名的文件名先走、定义了种子
符号的文件其次、同名只留路径最浅的一份（插件的、不留应用的）。

名次按集合顺序取。修法是全部按名次的排序先把名次四舍五入到 9 位

63 分前面）。改成加分制：文件名与种子完全相同 +55、定义了种子符号

前四，req-core 仍是 9 个文件、三处缺口全在；`tests/test_floor.py`
另加前缀弱档用例（定义种子的文件排在只以前缀命名的文件前面）。

## 11. AIspec 借鉴四项（2026-11-24）

参考：某大型企业内部文章《AI CoE 创新探索四：大型存量系统智能开发 V1.0》
（内部 wiki，全文存本地）。
它讲存量系统智能开发，选的是“渐进式构建”——需求驱动、按需沉淀，
先搭当前任务的最小完备上下文，再靠知识飞轮滚动扩充；与本方案
“一个需求只备最小完备上下文”的思路一致，等于企业级重型版替轻量版
背了书。全文存 `~/workspace/req-code-kb-work/aispec-doc.md`。借鉴四项：

### ① 影响面（反向调用，改前看 blast radius）

AIspec 代码图谱的 impact 能力，在本工具里是反向调用图：
`reqkb/graph.py` 的 `reverse_edges` 把调用边倒过来，`build_context`
给每个种子文件算前 3 个调用者（按调用者 PageRank 排序），知识页
新增“影响面”一节——改种子文件之前先看改动最先波及谁。只影响呈现，
不改变检索，盲测重跑仍通过。

### ② 知识飞轮（harvest，真实改动记回来）

AIspec 的 harvest 是“已完成需求的制品回流进上下文库”。本工具的
`reqkb harvest` 是最小版：需求对应的 PR 合并后，把真实改动文件
清单（`--changed-files`，或 `--repo + --base + --head` 自动 diff）
与沉淀页的预测对照，命中 / 漏掉 / 多余记进页末“回流记录”，
`kb/index.json` 同步存一份结构化记录。沉淀的文件清单不动，
原始预测保持可审计；第二次 harvest 追加，不覆盖第一次。
实测：#3896 沉淀页对照真实改动 5 个文件，召回 4/5，唯一漏掉的是
改动前不存在的 `CHANGES.md`。

### ③ 二级索引（L1 首页 + L2 分来源页 + 页内目录）

AIspec 上下文库是两级索引 + 按需加载：L1 索引按阶段/范围筛条目，
目录条目再读 L2 索引（README 列文件清单与加载顺序），避免一次全量
加载。本工具的网站照搬这个分层：L1 是首页（按来源列卡片），L2 是
每来源一张索引页（`/<来源>/index.html`，带每页 token 总量与分级），
知识页顶部加“本页目录”（h2 锚点跳转）。静态站没有运行时加载，
分层的作用是让读者不用打开大页也能定位到小页。

### ④ 需求分级（full / lite / vibe）

AIspec 按需求复杂度选 AI Coding 模式（Full-SDD / Lite-SDD /
Skill Coding / Vibe Coding），避免过度工程化。本工具的
`build --level` 照搬这个分法：

| 分级 | 深度 | 预算 | 适用 |
| --- | --- | --- | --- |
| full | 种子 + 1 跳 + PageRank 2 跳 | 8000 / ≤10 文件 | 跨多文件、核心业务/安全逻辑 |
| lite | 种子 + 1 跳 | 4000 / ≤6 文件 | 单模块小修、简单 CRUD、已知逻辑 |
| vibe | 只给种子文件 | 2000 / ≤4 文件 | 文字修改、配置、UI 样式 |

`--budget` 可显式覆盖分级的预算。full 与旧默认行为完全一致
（盲测重跑通过，重建页与沉淀页清单一致）；分级嵌套
vibe ⊆ lite ⊆ full，见 `tests/test_levels.py`。

## 12. 企业内部 SDD 规范借鉴（2026-11-24）

与 §11 的 AIspec 文章是同一套——需求驱动、按需沉淀最小完备
上下文，先跑通一个需求，再靠知识飞轮滚动扩充。等于第二个独立
来源替这套思路背了书：重型企业版（SDD 规范）和轻量开源版

红线：这是企业内部材料。只借鉴思路和结构，用自己的话写；原文

### ① 上下文七个目录（目标形状，不改代码）

规范把项目上下文分成七个目录。本工具的沉淀物按下面这张表
对上去——现在缺的不是文件，是“每类知识放哪”的约定：

| 目录 | 是什么 | 本工具里对应什么 |
| --- | --- | --- |
| business | 业务目标、术语、规则、流程、边界场景 | 需求文档本身 + 群消息佐证（知识页的需求原文、群消息两节） |
| data | 数据模型、表关系、枚举字典、数据归属 | 需求文档里的数据说明；代码页里命中数据模型符号时自然带上 |
| engineering | 设计约束、编码规范、接口规范、测试策略 | 命中文件的命名与结构约定（检索时不另建，靠代码本身呈现） |
| security | 安全合规规范 | 同上；涉及安全逻辑的需求走 full 分级（§11④） |
| system | 架构、模块视图、分层模型、接口目录 | 调用链 Mermaid 图 + 命中文件表（知识页的调用链一节） |
| sdd | 流程清单与模板（指导 Agent 怎么执行各阶段） | 本方案自己：演示脚本、盲测方法（§10）、分级表（§11④） |
| changes | 按需求工单隔离的临时上下文 | `kb/requirements/<需求>.md`，一需求一页；做完经 harvest 归档 |

### ② 三步走构建法（新仓库落地顺序）

规范建议新项目按三步建上下文，本工具的盲测流程正好是同一套，
写成推荐顺序：

1. **模拟实战**：拿已上线（已合并）的需求跑通全流程，建成
   context base。本工具的盲测就是这一步：click #3896 / #3878
   两个已合 PR 当考题，输入只有需求描述。
2. **实战演练**：拿一个真实新需求跑通 build → ask → harvest，
   进一步建库。
3. **批量补充**：一次拿 10 个需求，只跑需求和设计两步，批量提
   业务术语、完善架构与索引。

需求怎么选：先挑占比最大的那类需求，中等规模（前后端代码都改
的那种）——太小练不出东西，太大一次啃不完。

### ③ 上下文工程师与审核闸门（角色，不是代码）

规范设了一个专职角色“上下文工程师”：懂业务、懂架构的人（通常
由开发组长或技术骨干转），对上下文质量全面负责；AI 工程师在
他建好的上下文上做需求。新增知识的流转是：AI 起草、人类核对，
做完一轮以 PR 方式交回上下文仓库，上下文工程师审过才合。

本工具的对应关系：知识库的维护人就是上下文工程师；`reqkb harvest`
记回流记录时，沉淀的文件清单不动、原始预测保持可审计（§11②），
回流记录本身由跑 harvest 的人当场核对——这里是把角色和“人审过
才算数”点名，工具层面不另加流程。

### ④ 分阶段攒知识（什么时候补什么）

规范按阶段列了知识积累的时机，本工具按同一张时间表对：

- 提案分析前：业务对象与术语、现有架构与模块说明、现有功能
  与接口说明——对应需求文档的标题 / 背景 / 验收标准三段。
- 方案设计前：技术栈说明、开发规范、工程代码结构、数据字典
  与实体关系、原子服务方法清单——对应 build 命中文件的选择
  （种子 + 调用邻居）。
- 原型开发前：设计系统与组件样式——前端类需求才需要，后补。
- 方案实现中：方法级细节——对应 harvest 把真实改动记回来。

### ⑤ OpenSpec 制品目录（下一步的选项，现在不做）

规范附录的 OpenSpec 制品目录：每个变更一个目录，内含
proposal（动机与范围）、specs（按能力拆的增量规格）、design
（技术方案）、tasks（可勾选清单），做完归档到 `changes/archive/`，
主规格更新到 `specs/`（长期基线）。

本工具的对应关系：需求文档 = proposal + specs，知识页 = design
的输入，回流记录 = archive。现在不改目录结构；如果以后团队要
走规格驱动流程，再按这个目录搭 `openspec/changes/`，那时
`examples/` 里的需求文档直接就是 proposal。

### 与 §11 的关系

§11 的 AIspec 文章和这份 SDD 规范是两个独立来源，讲同一套方法：
两级索引 + 按需加载（§11③）在这里也有对应——规范的 L1 索引按
阶段 / 范围筛条目，目录条目再读 L2 索引，用完可卸载。两边独立
印证了同一结论：上下文要分层、按需取，不是一次全量倒进去。
