# GBC 工作坊演示脚本：req-code-kb（约 10 分钟）

现场：11-26–28 GBC 工作坊，需求组。讲给非技术学员也能听懂，
技术术语都先打比方。演示仓库是 pallets/click（91 个 `.py` 文件），
需求是真实已合并的 PR #3896。

## 0. 演示前检查（提前 5 分钟）

```bash
cd req-code-kb
python3 -m reqkb --help          # 确认能跑
CLICK_PRE3896=<改动前 checkout> CLICK_PRE3878=<改动前 checkout> \
    python3 tests/test_blind.py  # 确认两用例通过（约 5 秒）
```

两个改动前 checkout 须事先备好（本机在
`~/workspace/req-code-kb-work/click-pre3896` 与 `click-pre3878`）；
没设环境变量时脚本会跳过用例、只报“0 个用例通过”，别当成真通过。

断网也不怕：本脚本每段都贴了“预期输出”，现场跑不出来就念预期
输出、讲逻辑——盲测结果和知识页都已沉淀在仓库里，不是现场现算。

## 1. 开场：为什么不整仓倒进去（1 分钟）

> “做一道菜只备齐这道菜要用的料，不把整个菜市场搬进厨房。
> click 这个仓库有 91 个 Python 文件，一个需求其实只碰其中几个。
> 把整仓倒给 AI，AI 要在 91 个文件里找答案，又贵又容易找错。”

两个证据数字（都核实过出处，讲的时候要带“相关 / 最多”的限定）：

- SWE-Explore 基准（2026）：上下文效率与修复成功率的相关系数
  Pearson r = +0.95——找得越准、废话越少，修好的可能性越高。
  （这是相关性，不是保证每单都修好。）
- 微软 FastContext（2026）：只给主 Agent 最小证据，token 最多降
  60%、解决率最多升 5.5%。（“最多”是论文原话的 up-to 口径。）

第三个佐证在企业内部：一家大型企业的《AI Coding SDD 开发规范 V3.1》讲存量
系统智能开发，用的也是同一套思路——先为当前需求建最小完备上下文
跑通全流程，再靠知识飞轮滚动扩充。论文、公司规范、这个小工具，
三边讲的是同一件事。

## 2. 需求进来（2 分钟）

打开 `examples/click-req-3896.md`，念一遍需求（说人话版）：

> “测试里想在同一次调用中，既设定终端支持情况、又设定命令
> 上下文的 `color`，但 `CliRunner.invoke()` 自己占了 `color` 这个
> 名字，传不进去。需求：加一个 `context_settings` 参数透传。”

提一句格式：需求文档按 spec-kit 模板写（标题 / 背景 / 验收标准
三段），机器才能从反引号里把 `CliRunner`、`invoke`、`Context`
这些标识符摘出来当种子。

## 3. 跑 build：134 个文件 → 10 个文件（2 分钟）

```bash
python -m reqkb build --repo <click 仓库路径> \
    --req examples/click-req-3896.md \
    --messages examples/messages-3896-sample.json \
    --repo-url https://github.com/pallets/click --ref 08b803c --yes
```

`--messages` 带的是群消息样本文件（虚构格式，见 §4 第 4 点）；
`--ref` 定死提交，链接才精确到行。带上这三个参数，现场跑出来
的页与仓库里沉淀的页逐字相同——跑了也不怕盖掉沉淀页。

预期输出（实测）：

```text
需求 click-req-3896：种子 ['CliRunner', 'invoke', 'Context', 'color', 'context_settings']，分级 full
仓库共 134 个文件；最小上下文 10 个文件，约 7216 tokens（预算 8000）
  [0跳] src/click/core.py ...
  [0跳] src/click/testing.py ...
  ...
已沉淀：kb/requirements/click-req-3896.md
```

讲三个点：

- **种子**：需求里点名的标识符是起点，不是全文关键词。
- **跳数**：沿着调用关系走 1 步的邻居必进，走 2 步的只进重要的
  （PageRank 打个比方：像论文引用一样，越多人调用的函数越重要）。
- **预算**：8000 tokens 上限，超了从低往高砍；大函数只截前 60 行
  看形状，不整段搬。

再提一句 `--yes`：不加这个参数，程序会先打印候选清单、等人按 y
确认才入库——人确认再沉淀，机器不擅自定。

## 4. 知识页：沉淀物长什么样（2 分钟）

打开 `kb/requirements/click-req-3896.md`，逐段指：

1. 需求原文（带来源链接）。
2. 相关文件 / 函数表：每个文件带 `文件:行号` 的 GitHub 链接，
   精确到提交（`08b803c`）。
3. 调用链 Mermaid 图：`CliRunner.invoke` 调了谁，一眼看到。
4. 群消息佐证：飞书群里王鹏和张峰讨论这个冲突的三条消息
   （演示用的是虚构格式样本，真实群消息导出后按同样格式进库）。
5. 影响面：改这份文件会波及谁——比如改 `src/click/testing.py`
   会波及哪些测试，现场指一行念出来（这是 11-24 晚新加的，
   老页没有这一节）。
6. 验收清单。
页脚还写着“分级：full——完整（跨多文件、核心逻辑）”：这份上下文
是按完整档建的；小修用 `--level lite`（4000 tokens）、随手改用
`--level vibe`（2000 tokens，只给种子文件）。

再打开 `kb/index.json` 指一下：`click-req-3896` 和
`click-req-3878` 的 `shared_with` 互相挂着——`src/click/testing.py`
两个需求都要用，只存一份，不复制两份。这就是“需求越多库越完善”，
重叠的部分自动归并。

## 5. 问答：拿新需求现场问一句（1.5 分钟）

```bash
python -m reqkb ask --kb kb --q "CliRunner.invoke 怎么传 context 设置？"
```

预期：Top-5 片段带出处和分数（第一条 0.261，正好是需求那一节；
分数比早期的 0.797 低，是因为知识页多了“影响面”一节、整页变长
了，排位没变），然后是一段拼好的提示词。把提示词贴给现场的大模型问一句，答案
当场出来。强调：MVP 不内置大模型调用——检索和拼提示词是确定的，
模型那一步人肉走，现场少一个翻车点。

## 6. 验收：怎么证明这不是摆拍（1.5 分钟）

```bash
CLICK_PRE3896=<改动前 checkout> CLICK_PRE3878=<改动前 checkout> \
    python3 tests/test_blind.py
```

讲方法（这是整个演示最值得学的一点）：

> “我们不是拿已经合入的代码跑一遍自证，而是回到改动之前——
> 仓库切到 PR 合并前的那个提交，输入只有需求描述，看系统能不
> 能找回真实改动的文件。”

实测结果（2026-11-24，含晚上的种子定义文件保底改动后重测）：

| 用例 | 输出 | 命中 |
|---|---|---|
| #3896 | 10 个文件，6383 tokens | 3/5，核心文件 `src/click/testing.py` 在内 |
| #3878 | 10 个文件，5405 tokens | 2/4，核心文件在内 |

诚实说漏掉的：两次都漏了 `docs/testing.md` 和 `CHANGES.md`。
`CHANGES.md` 的条目是 PR 本身加的，改动前不存在，原则上不可召回；
`docs/testing.md` 是已知局限，长文档信号被稀释，写在方案 §10 里了。

## 7. 收尾：学员带走的三句话（1 分钟）

1. 按需求建库，不按整仓倒；一个需求只备它要用的料。
2. 最小上下文 = 种子 → 调用图走一两步 → 预算裁剪；人确认再入库。
3. 验收要盲测：回到改动前，看新需求能不能找回真实改动文件。

现场练习（如果时间够）：学员拿自己项目的一份需求文档，套
spec-kit 三段格式写一遍，当场跑 `build` 看最小上下文。

## 讲稿要点（备用，问答环节）

- **“死需求、死代码不用管，谁来判定什么是死的？”**
  MVP 不自动判定生死，只记“最后被引用时间 + 引用次数”，90 天
  零引用标“疑似沉寂”，删不删由人定。
- **“这跟 deepwiki / Repomix 有什么区别？”**
  它们是先把整仓倒进去再问；我们是反过来的，先有需求再建库，
  需求越多库越完善。Aider 的 repo map 只借了算法思路（抽符号 →
  构图 → PageRank → 按预算裁剪），代码是自己写的，零依赖。
- **“许可证有没有坑？”**
  SocratiCode 是 AGPL-3.0，只看了思路，没抄代码；Sweep 新版是
  BSL，只参考思路。项目本身 MIT。
- **“飞书群消息怎么进库？”**
  只做导出文件进库，只索引跟需求相关的片段，不整群倒灌；
  只读不写，不自动发消息。
