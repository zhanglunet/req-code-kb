## 一、背景：为什么不整仓倒进去

做一道菜只备齐这道菜要用的料，不把整个菜市场搬进厨房。一个需求其实只碰仓库里的几个文件，把整仓代码倒给 AI，又贵又容易找错。两个证据数字（都核过原始出处）：

- **SWE-Explore 基准（2026，arXiv:2606.07297）：**上下文效率与修复成功率的相关系数 Pearson r = **+0.95**。找得越准、废话越少，修好的可能性越高。这是相关性，不是每单都修好的保证。
- **微软 FastContext（2026，arXiv:2606.14066）：**只给主 Agent 最小证据，token **最多降 60%**、解决率**最多升 5.5%**。“最多”是论文原话的 up-to 口径，token 只算主 Agent 的轨迹。

目标：一个需求建一个“最小完备上下文”知识页；需求越多，库越完善；三路来源——代码仓库、需求文档、飞书群消息。

## 四、实现：它怎么做

### 流程

1. **解析：**标准库 `ast` 抽符号（函数 / 类 / 调用关系），`.md` 文档只做文本索引。
2. **排序：**调用关系构图 + PageRank。打个比方：像论文引用一样，越多人调用的函数越重要。
3. **检索：**需求文档反引号里的标识符当种子 + TF-IDF；1 跳邻居必进，2 跳按 PageRank 筛；默认 8000 tokens 预算，超了从低往高砍；单文件最多 5 个片段、1200 tokens；大函数只截前 60 行看形状。
4. **沉淀：**人确认候选清单后才入库（`--yes` 跳过确认）；每页固定结构：需求原文、相关文件 / 函数（带 `文件:行号` 链接）、调用链 Mermaid 图、群消息佐证、验收清单；重叠的文件只存一份，多需求共享（`kb/index.json` 的 `shared_with`）。
5. **问答：**TF-IDF 取 Top-5 片段带出处，拼成提示词打印出来——MVP 不内置大模型调用，现场把提示词贴给模型问一句。

### 模块

| 模块 | 职责 |
|---|---|
| `reqkb/parse.py` | ast 符号 / 调用 / import 抽取，片段截断 60 行并标明 |
| `reqkb/graph.py` | 调用图（同名优先同文件）、PageRank（阻尼 0.85） |
| `reqkb/retrieve.py` | TF-IDF（符号名权重 ×3）+ 种子加分 + 预算裁剪 |
| `reqkb/render.py` | 固定结构知识页 + Mermaid 调用链 + 群消息证据 |
| `reqkb/qa.py` | TF-IDF 问答：Top-5 带出处 + 拼装提示词 |
| `reqkb/cli.py` | `build` / `ask` / `eval` 三个命令 |

### 飞书群消息（第三路来源）

群消息导出成 JSON（`--messages`），只索引与需求关键词相关的片段，不整群倒灌。`examples/feishu-sample.json` 是明确标注的虚构格式样本。只读不写，不自动发消息。

## 五、盲测：怎么证明这不是摆拍

**方法：**不是拿已合入的代码跑一遍自证，而是回到改动之前——仓库切到 PR 合并前的提交，输入只有需求描述（改动文件已隐去），看系统能不能找回真实改动的文件。

| 用例 | 输出 | 命中 | 漏掉 |
|---|---|---|---|
| click #3896<br>给 `CliRunner.invoke` 加 `context_settings` | 10 个文件，6823 tokens | **3/5**：`src/click/testing.py`、`tests/test_testing.py`、`tests/test_termui.py` | `docs/testing.md`、`CHANGES.md` |
| click #3878<br>`\x04` / `\x1a` 回显为 `^D` / `^Z` | 10 个文件，5017 tokens | **2/4**：`src/click/testing.py`、`tests/test_testing.py` | `docs/testing.md`、`CHANGES.md` |

**验收线怎么定的：**`CHANGES.md` 的条目是 PR 本身加的，改动前不存在，原则上不可召回，所以 #3896 最高可命中 4/5、#3878 最高 3/4；验收线（≥3/5、≥2/4）就是按这个上限定的。两项全部通过（`python3 tests/test_blind.py`）。

**已知局限，不藏着：**`docs/testing.md` 两次都没进前 10——长文档的 TF-IDF 信号被整篇稀释，50 行窗口取最密一段已有所缓解，但还没完全解决；下一步可把文档按小节切分再索引。

## 六、测试中抓出的两个真 bug

| 问题 | 表现 | 修法 |
|---|---|---|
| 种子名只取最后一段 | `CliRunner.invoke` 被切成 `invoke`，最关键的 `CliRunner` 丢了，种子识别全错 | 点分标识符全段 + 最后一段都当种子 |
| 预算逻辑反了 | 第一个大文件独吞 8000 tokens，后面的文件一个都进不来 | 先按分数排序、按“最小分片”分摊，砍掉的记日志可查 |

修完后盲测两项才全过。另修了一个小毛病：知识页的需求原文会重复一个一级标题（页面标题与需求文档标题撞了），已在渲染时去掉。
